### 2. What Both Claude & Codex Missed

#### **[BLOCKER] The Ephemeral `/tmp` File Loss Risk**
*   **Quote:** *"Review saved at `/tmp/codex-welcome-output.txt` and `/tmp/gemini-welcome-output.txt`."*
*   **Finding:** Saving critical design artifacts (the compressed 3-email sequence reviews) in the global `/tmp/` directory means they will be destroyed when the container/VM session is recycled. The next Claude session will have no access to these files. They must be moved into the workspace (e.g., inside `.gemini/` or a `docs/` folder) to prevent total loss of context.

#### **[MAJOR] Next.js Static Compilation vs. Runtime Worker Secrets Conflict**
*   **Quote:** *"`STAGEFIT_V2_ENABLED=true` is a Worker runtime secret... Read via `process.env.STAGEFIT_V2_ENABLED` in Server Component (works because OpenNext maps Worker env to process.env for SSR)"*
*   **Finding:** Because Worker secrets are only injected at runtime inside the deployed Worker, they are `undefined` during the Next.js build phase in CI/CD. If the Server Component or containing page is statically generated, Next.js will bake the build-time value (`undefined`/`false`) into the static HTML. Unless the page is explicitly marked as dynamic (e.g., `export const dynamic = 'force-dynamic'`), the feature flag will remain completely non-functional at runtime.

#### **[MAJOR] Contradictory "Beehiiv Verification" and "Subscriber in Beehiiv → then Kit" Flow**
*   **Quote:** *"API connection verified, subscriptions work, custom fields created (12)"* and *"Production form tested end-to-end (footer → "You're in!" → subscriber in Beehiiv → then Kit)"*
*   **Finding:** This is a major logical contradiction. If the codebase was fully migrated to Kit and `KIT_API_KEY` *replaced* `BEEHIIV_API_KEY` in the environment, the application should no longer be able to write to Beehiiv. If testing the production form actually resulted in a subscriber appearing in Beehiiv, then the live site is either still running stale Beehiiv-dependent code or the verification log is copy-pasted/fabricated. Furthermore, "custom fields (12)" is a Kit setup; Beehiiv does not have these.

#### **[MINOR] Misleading "404 on Creator Plan" Explanation for Subscriber Delete**
*   **Quote:** *"Subscriber DELETE returns 404 on Creator plan (may be plan-restricted)"*
*   **Finding:** A `404 Not Found` API response indicates an incorrect URL endpoint or an invalid subscriber ID. A plan restriction or authorization failure would return `403 Forbidden` or a billing error. Labeling a 404 as "plan-restricted" is misleading and will waste the next session's time checking dashboard tiers instead of debugging the URI path or subscriber IDs.

#### **[MINOR] Kit Automation "Signup" Trigger Misunderstanding**
*   **Quote:** *"(a) configure Kit automation in dashboard with 'signup' trigger"*
*   **Finding:** Subscribers added directly via the API (`POST /v4/subscribers`) do not fire visual "form signup" triggers in Kit because they are not submitting a native Kit form. Recommending a "signup" trigger for API-driven subscribers is a configuration mistake; the automation must be triggered by "Tag added" (`architect-brief`).
